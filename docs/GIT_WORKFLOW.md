# Git 使用约定（MusicGraph 项目）

> 给非专业工程师看的极简版。目标：够用、不出错、能回退。

## 一、心智模型

- **Git = 游戏存档系统**：`git commit`（提交）= 按存档键；没存档 = 白干。
- **master = 稳定主线**：永远保持"能跑、你认可"的状态。
- **分支 = 平行世界**：随便折腾，不满意删掉，不影响主线。

## 二、最常用命令

| 想做什么 | 命令 |
|---|---|
| 看状态（改了哪些文件） | `git status` |
| 开新分支并切过去 | `git switch -c 分支名` |
| 回到 master | `git switch master` |
| 看所有分支 | `git branch` |
| 合并分支到当前分支 | `git merge 分支名` |
| 删除已合并的分支 | `git branch -d 分支名` |
| 提交当前改动 | `git add -A` 然后 `git commit -m "说明"` |
| 看提交历史 | `git log --oneline` |

## 三、关键决策规则：一个方向做完再开下一个 vs 并行（worktree）

**只用一条规则判断：**

> 方向 A 和方向 B 会不会改到**同一批文件**？
> - **会**（例如都改 `web/app.js`、`web/index.html`、`web/style.css`）→ **串行**：先完成 A、提交，再从完成后的新基线开始 B。交互问题自然消失。
> - **不会**（例如 A 只改 Python 脚本、B 只改前端页面）→ 才考虑用 worktree 并行。

**为什么"有交互"时不要并行：**
并行（worktree）只是把"交互"推迟到最后，变成"合并冲突"集中爆发；两边都在同一批文件上改过时，最后要手工解决一堆冲突，还得同时理解两边逻辑，个人项目扛不住。

## 四、本项目当前约定

1. `master` = 稳定版；新方向一律开分支。
2. Codex 对话自动建的分支叫 `codex/xxx`（如 `codex/ui-refine`），代表某个对话的方向。
3. **一个工作文件夹同一时间只做一个方向**。想换方向，先提交/或切走，再开工。
4. 数据库备份文件（`music_graph_backup_*.db`）不入库，Git 本身就是版本管理。
5. 试验分支命名建议：`try-xxx`（如 `try-3d-home`）表示可能放弃的试验；成功后再合并回 master。

## 五、冲突怎么办（不用慌）

- 分支不重要 → 放弃合并，`git branch -D 分支名`。
- 冲突复杂 → 让 Codex 帮忙解决，会把两边改动展示出来再定。
- 冲突简单 → 打开文件，找 `<<<<<<<` 和 `>>>>>>>` 标记，删掉不要的、保留要的。
